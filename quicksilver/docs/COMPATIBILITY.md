Fidelity is the overlap between the recovered code and the original program the fixture was made from (identifier names ignored). Behaviour compares what the recovered script prints with what the
obfuscated one printed, on a real Lua (PUC 5.1 / LuaJIT / 5.4 through `lupa`). A technique is **supported** when fidelity is at least 85% and behaviour matches; **partial** when it is better than before
but short of that; **unsupported** otherwise. Families without fixtures are signatures only (**experimental** or **unsupported**): nothing was run and nothing is claimed.

**Limits**

* Vmify (the flattened register VM) is unflattened: the dispatcher is walked, every block is turned back into statements and the control flow is rebuilt (also for the two Vmify layers of the Strong preset). * String decoders (EncryptStrings, ConstantArray) are evaluated only when sandboxed evaluation is switched on.
* Recovery of the Strong preset takes several seconds in the browser (the two layers are rebuilt one after the other).

## IronBrew 2

Open-source (MIT) Lua 5.1 obfuscator in C# that compiles a script with luac and re-emits it as a custom register VM plus a compressed, XOR-masked program string.

**Status:** supported (real-output). The prelude (LZW + XOR deserialiser, wrapper function names) is matched structurally; the opcode handlers are matched by alpha-equivalent form against the handler templates in IronBrew 2's own C# source.

| Configuration | Status | Fidelity before → after | Same behaviour | Mean time |
|---|---|---|---|---|
| default (preset) | supported | 4% → 91% | 8 / 8 | 49 ms |
| plain (preset) | supported | 8% → 93% | 8 / 8 | 38 ms |
| mutate (preset) | supported | 6% → 93% | 8 / 8 | 38 ms |
| super (preset) | supported | 5% → 93% | 8 / 8 | 46 ms |
| flow (preset) | supported | 8% → 91% | 8 / 8 (5 tool output broken) | 41 ms |
| strings (preset) | partial | 3% → 77% | 8 / 8 | 534 ms |
| lineinfo (preset) | supported | 4% → 91% | 8 / 8 | 49 ms |
| nocompress (preset) | supported | 4% → 91% | 8 / 8 | 52 ms |

**Limits**

* Recovery reads the embedded chunk instead of running the VM: handlers are identified by shape, operand transforms are solved symbolically, the Lua 5.1 chunk is rebuilt and decompiled. A handler that matches no template stops the recovery with an error instead of guessing.
* Local variable names, comments and the original function layout are not in the bytecode, so they are not recoverable (names are regenerated; some local functions come back as expressions).
* The "strings" option decrypts every literal with a routine written out in place. Recovery finds those stretches (only constants, only pure standard functions, no closures) and replaces each by the text it computes, using the sandbox interpreter on that stretch alone; it needs no consent because nothing but the stretch is run. Other register-reuse noise remains, so the result is partial.
* The "flow" option of the real tool produced output that does not run correctly on its own for five of eight samples (see the "tool broken" column); recovery there is judged against the original program, not against the broken output.
* Only IronBrew 2 as built from the public MIT source is covered. Forks that change the VM template or the serialiser need their own templates.

## Loadstring packers

A class of packers, not one tool: the program is encoded and handed to loadstring. The examples were written for this project from the documented encodings; they are not the output of any real obfuscator.

**Status:** supported (synthetic). Not a single signature: the loadstring-layer trait is reported. Recovery is measured on packers written for this project (tests/corpus/tools/gen_loaders.mjs), not on any real tool.

| Configuration | Status | Fidelity before → after | Same behaviour | Mean time |
|---|---|---|---|---|
| ascii (preset) | supported | 15% → 100% (needs sandbox) | 6 / 6 | 7 ms |
| hex (preset) | supported | 10% → 100% (needs sandbox) | 6 / 6 | 6 ms |
| binary (preset) | supported | 15% → 100% (needs sandbox) | 6 / 6 | 7 ms |
| url (preset) | supported | 10% → 100% (needs sandbox) | 6 / 6 | 6 ms |
| base64 (preset) | supported | 23% → 100% (needs sandbox) | 6 / 6 | 8 ms |
| xor (preset) | supported | 5% → 100% (needs sandbox) | 6 / 6 | 16 ms |
| reverse (preset) | supported | 3% → 100% | 6 / 6 | 4 ms |
| escapes (preset) | supported | 3% → 100% | 6 / 6 | 5 ms |
| charcodes (preset) | supported | 3% → 100% | 6 / 6 | 8 ms |
| pieces (preset) | supported | 5% → 100% | 6 / 6 | 4 ms |
| layered (preset) | supported | 23% → 100% (needs sandbox) | 6 / 6 | 11 ms |

**Limits**

* Literal, folded and string.char payloads are unwrapped without running anything. A payload computed by a decoder (hex, base64, XOR, URL escapes, ...) is read only when sandboxed evaluation is on, and only when the script is nothing but that loader: the other statements may use standard libraries and local variables, nothing else.
* A script that does anything else around the loader (touches the game, writes globals, prints) is never replaced wholesale; Dump still shows the text it loads.
* Payloads that read `...`, return values, or need the network (`HttpGet`) are left alone. Compiled Lua 5.1 and 5.4 payloads are decompiled.
* These are generic packers I wrote from the encodings other tools document. Whether a real obfuscator that uses the same encodings is handled depends on its decoder staying within the standard libraries; none of them was run.

**Documented techniques with no fixture:** decimal escapes, string.char, string pieces
