# Compatibility

Generated by `tools/build-compat.mjs` from `tests/results/*.json` (400 fixtures, engine 1.0.0). Do not edit by hand.

Fidelity is the overlap between the recovered code and the original program the fixture was made from (identifier names ignored). Behaviour compares what the recovered script prints with what the
obfuscated one printed, on a real Lua (PUC 5.1 / LuaJIT / 5.4 through `lupa`). A technique is **supported** when fidelity is at least 85% and behaviour matches; **partial** when it is better than before
but short of that; **unsupported** otherwise. Families without fixtures are signatures only (**experimental** or **unsupported**): nothing was run and nothing is claimed.

**Limits**

* Vmify (the flattened register VM) is unflattened: the dispatcher is walked, every block is turned back into statements and the control flow is rebuilt (also for the two Vmify layers of the Strong preset). * String decoders (EncryptStrings, ConstantArray) are evaluated only when sandboxed evaluation is switched on.
* Recovery of the Strong preset takes several seconds in the browser (the two layers are rebuilt one after the other).

## IronBrew 2

Open-source (MIT) Lua 5.1 obfuscator in C# that compiles a script with luac and re-emits it as a custom register VM plus a compressed, XOR-masked program string.

**Status:** supported (real-output). The prelude (LZW + XOR deserialiser, wrapper function names) is matched structurally; the opcode handlers are matched by alpha-equivalent form against the handler templates in IronBrew 2's own C# source.

| Configuration | Status | Fidelity before → after | Same behaviour | Mean time |
|---|---|---|---|---|
| default (preset) | supported | 4% → 91% | 8 / 8 | 49 ms |
| plain (preset) | supported | 8% → 93% | 8 / 8 | 35 ms |
| mutate (preset) | supported | 6% → 93% | 8 / 8 | 33 ms |
| super (preset) | supported | 5% → 93% | 8 / 8 | 37 ms |
| flow (preset) | supported | 8% → 91% | 8 / 8 (5 tool output broken) | 35 ms |
| strings (preset) | partial | 3% → 77% | 8 / 8 | 469 ms |
| lineinfo (preset) | supported | 4% → 91% | 8 / 8 | 41 ms |
| nocompress (preset) | supported | 4% → 91% | 8 / 8 | 43 ms |

**Limits**

* Recovery reads the embedded chunk instead of running the VM: handlers are identified by shape, operand transforms are solved symbolically, the Lua 5.1 chunk is rebuilt and decompiled. A handler that matches no template stops the recovery with an error instead of guessing.
* Local variable names, comments and the original function layout are not in the bytecode, so they are not recoverable (names are regenerated; some local functions come back as expressions).
* The "strings" option decrypts every literal with a routine written out in place. Recovery finds those stretches (only constants, only pure standard functions, no closures) and replaces each by the text it computes, using the sandbox interpreter on that stretch alone; it needs no consent because nothing but the stretch is run. Other register-reuse noise remains, so the result is partial.
* The "flow" option of the real tool produced output that does not run correctly on its own for five of eight samples (see the "tool broken" column); recovery there is judged against the original program, not against the broken output.
* Only IronBrew 2 as built from the public MIT source is covered. Forks that change the VM template or the serialiser need their own templates.

## Loadstring packers

A class of packers, not one tool: the program is encoded and handed to loadstring. The examples were written for this project from the documented encodings; they are not the output of any real obfuscator.

**Status:** supported (synthetic). Not a single signature: the loadstring-layer trait is reported. Recovery is measured on packers written for this project (tests/corpus/tools/gen_loaders.mjs), not on any real tool.

|---|---|---|---|---|
| ascii (preset) | supported | 15% → 100% (needs sandbox) | 6 / 6 | 7 ms |
| hex (preset) | supported | 10% → 100% (needs sandbox) | 6 / 6 | 7 ms |
| binary (preset) | supported | 15% → 100% (needs sandbox) | 6 / 6 | 8 ms |
| url (preset) | supported | 10% → 100% (needs sandbox) | 6 / 6 | 8 ms |
| base64 (preset) | supported | 23% → 100% (needs sandbox) | 6 / 6 | 8 ms |
| xor (preset) | supported | 5% → 100% (needs sandbox) | 6 / 6 | 19 ms |
| reverse (preset) | supported | 3% → 100% | 6 / 6 | 6 ms |
| escapes (preset) | supported | 3% → 100% | 6 / 6 | 6 ms |
| charcodes (preset) | supported | 3% → 100% | 6 / 6 | 9 ms |
| pieces (preset) | supported | 5% → 100% | 6 / 6 | 6 ms |
| layered (preset) | supported | 23% → 100% (needs sandbox) | 6 / 6 | 13 ms |

**Limits**

* Literal, folded and string.char payloads are unwrapped without running anything. A payload computed by a decoder (hex, base64, XOR, URL escapes, ...) is read only when sandboxed evaluation is on, and only when the script is nothing but that loader: the other statements may use standard libraries and local variables, nothing else.
* A script that does anything else around the loader (touches the game, writes globals, prints) is never replaced wholesale; Dump still shows the text it loads.
* Payloads that read `...`, return values, or need the network (`HttpGet`) are left alone. Compiled Lua 5.1 and 5.4 payloads are decompiled.
* These are generic packers I wrote from the encodings other tools document. Whether a real obfuscator that uses the same encodings is handled depends on its decoder staying within the standard libraries; none of them was run.

**Documented techniques with no fixture:** decimal escapes, string.char, string pieces

## Colisseum

Open-source (AGPL-3.0) Lua / Luau obfuscator written in Lua (de-TourLLC). Presets easy, medium, hard and full are source-level; total and fortress compile the program for a VM.

**Status:** partial (real-output). Signatures verified against output of the real tool for every preset: the credit line, the error brand, the coli_ names, the tamper guard block and the VM entry call. The AGPL-3.0 licence of the tool does not allow committing its output, so the fixtures are generated locally (tests/corpus/tools/gen_external.py, run through the isolated runner) and the tests that use them skip when they are absent.

| Configuration | Status | Fidelity before → after | Same behaviour | Mean time |
|---|---|---|---|---|
| easy (preset) | supported | 67% → 100% | 8 / 8 | 6 ms |
| medium (preset) | supported | 11% → 100% (needs sandbox) | 8 / 8 | 21 ms |
| hard (preset) | supported | 10% → 100% (needs sandbox) | 8 / 8 | 22 ms |
| full (preset) | supported | 9% → 100% (needs sandbox) | 8 / 8 | 25 ms |
| total (preset) | unsupported | 3% → 3% | 0 / 8 | 1381 ms |
| fortress (preset) | unsupported | 3% → 3% | 0 / 8 | 212 ms |

**Limits**

* easy, medium, hard and full are source-level: the tamper guard is recognised by its strings and removed without being run, the string decryptor is evaluated in the sandbox, and the junk branches are dropped. The output prints what the original program prints; names are guesses from use.
* The decryptor multiplies past 2^53 and was written for Lua 5.4 integers (it gives noise on Lua 5.1, LuaJIT and Luau doubles). The sandbox therefore evaluates it both ways and keeps the reading that is text; if neither is, the strings are left encoded and the report says so. Without the sandbox the strings stay encoded.
* total (native VM) and fortress (register VM with an encrypted bytecode blob) are detected from the VM entry call and flagged as not recovered: the program exists only as data for an interpreter. Recovery is not attempted.
* The behavioural trace is stopped by the tamper guard of every preset except easy, because the trace’s stand-in environment defines executor functions and the guard counts them (error 0x6B0C). Remove the guard first (medium, hard, full: Deobfuscate, then Trace the result). In the plain sandbox total runs to the end and fortress stops at 0x3E44 (the guard sees the sandbox’s debug library is not native).
* The total and fortress fixtures only run without an instruction-count hook, on LuaJIT: their anti-tamper treats a hook as an attack, so they were verified with tests/corpus/tools/run_lua_nohook.py.

**Documented techniques with no fixture:** constant arrays / split strings, control-flow flattening and opaque predicates

Open-source (MIT) obfuscator based on IronBrew 2 (Zaenalos): the script is compiled with luac 5.4 and run by a generated VM.

**Status:** unsupported (real-output). Signatures from the tool’s source and verified on its output: the wrapper (function(pack, move, unpack, env, pCall, Err) ...) and the VM names lua_wrap_state, run_vm and hexToString.

| Configuration | Status | Fidelity before → after | Same behaviour | Mean time |
|---|---|---|---|---|
| default (preset) | unsupported | 4% → 4% | 2 / 8 (6 tool output broken) | 542 ms |

**Limits**

* The program is compiled with luac 5.4, its constants are encrypted, dead instructions and super-operators are added, and a generated VM runs the hex-encoded stream. It is detected and flagged as not recovered; no lifter for its instruction format was written.
* The behavioural trace works (the sandbox gained Lua 5.4 bitwise operators, goto, string.unpack, _ENV and integer arithmetic for it) and reproduces what the original program does for every fixture where the tool’s own output is correct. A trace describes one run; it is not the original source.
* Zenfus’s own output misbehaves for six of the eight programs (see the "tool broken" column); those fixtures are excluded from behaviour claims.

## Simple-Lua-Obfuscator

Small obfuscator (CloudHub111, no licence file): the script is written as codes, base64-encoded, cut into five-character pieces and loaded at run time.

**Status:** supported (real-output). The fixed helper names of the tool’s template (_0x38ndf, _0x93mdw, _0x47fjs, _0x62tdg, _0x29dke). The repository has no licence file, so the fixtures are generated locally and not committed.

| Configuration | Status | Fidelity before → after | Same behaviour | Mean time |
|---|---|---|---|---|
| default (preset) | supported | 6% → 100% (needs sandbox) | 8 / 8 | 54 ms |

**Limits**

* The program is written as decimal escapes, base64-encoded, cut into five-character pieces and loaded at run time. With the sandbox on, the loader is run alone to read the text it hands to load, and that text replaces the script. Without the sandbox the layer is only detected.
* This is a loader-style packer: anything the loader does besides decoding (touching other globals, printing) stops the replacement. Variable names of the original are kept because the payload is the original source.
