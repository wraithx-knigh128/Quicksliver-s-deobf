* **2.0.0** not supported: default (unsupported, –, 1 output(s) the tool wrote that do not parse); all (unsupported, –, 1 output(s) the tool wrote that do not parse)

**Limits**

* The bytecode-encoding module hides a compiled Lua 5.4 chunk behind a hex string and an offset. With sandboxed evaluation on, the chunk is read out, decompiled and put in place of the script; without it the module is only detected. The chunk carries debug information, so the original local and function names come back.
* The virtual-machine module (revisions 1.6.2 and later, VMGenerator.lua) is read back without running anything: the program text (base-94 digits over a shuffled alphabet, bytes written as pairs with a backslash) is decoded, the Lua 5.1 chunk in it is decompiled and put where the interpreter was started, and the interpreter’s declarations are dropped. Constants the tool’s serialiser measured with `#` and therefore left out when a nil sits among them are put back only where the instructions leave one possible slot; where they leave more than one the choice is ranked and the report says so, and where constants are really missing from the file the module is refused (sample s06 of the corpus is such a case: the values are not in the output the tool wrote). Names are the decompiler’s: the original ones are not in the data.
* The virtual-machine module of revisions 1.5 and 1.6 (Compiler/c.lua, a different interpreter and data format) is detected and flagged; its program is not recovered (10% fidelity, measured).
* Function inlining is undone: closures pasted at each call site become one local function again, placed where the hole the tool left for the deleted definition is when the text still has it. Original function names are not recoverable.
* The renaming module renames `self` in method bodies without declaring it (a defect of the tool): the renamed global is read as `self` again when every use of it is inside a method that does not use `self`, and the report says that it was inferred.
* Revisions 1.5 and 1.6: the coin-flip guard of the control-flow module is removed; the older modules (string encoding, garbage code, opaque predicates, wrappers) share their patterns with later revisions and are measured per revision in the Versions table.
* The tool itself produced non-equivalent output for some module/sample pairs (see the "tool broken" column); those cases are excluded from behaviour claims.

**Documented techniques with no fixture:** Caesar string encoding

## MoonVeil

Commercial obfuscator (moonveil.cc) with selectable virtualisation, function encryption and control-flow flattening (macros MV_VM, MV_ENC_FUNC, MV_CFF, MV_OMIT). One real output was read (banner "generated using MoonVeil 2.0.25"): functions lifted into a table, flattened bootstrap code, Z85 + XOR strings, bit32 expressions for numbers, and VM-compiled functions stored as one compressed Z85 text (read back from that data by the VM reader when the interpreter has the shape of the script that was studied).

**Status:** partial (signature). Banner by its text (the version in it is what the file claims) and the table-and-permutation shape structurally. Five scripts of four versions were read, none of them stored here: 1.4.5, 2.0.25 (supplied by a user), 2.0.26 and 2.1.0 (two scripts) from public deobfuscator repositories. No MoonVeil output could be generated (the tool is closed and hosted), so there is no scorecard row; per-version records are in data/research/format-records.json and are re-measured by tools/formats/measure.mjs when the scripts are present.

**Detection on real scripts:** 76 of 76 files filed under MoonVeil in the public collection (https://github.com/vyxonq-dev/obfuscator-samples, commit `82e582fcdd`) were identified as MoonVeil; the version read from the script matched the collection's version directory in 58 of 58. The collection's labels are its uploaders' and are noisy; a file our rules call something else was looked at before being counted as a miss.

**Limits**

* Read back statically: the strings (Z85 text plus an XOR cipher), the numbers (bit32 expressions) and the table of cells, which makes the program’s plain Lua readable. The bootstrap permutation is read in both spellings seen (2.0.25 and 2.0.26/2.1.0, where the flattened bootstrap scrambles the statements), and the cell layout (where the index, the value and the self reference sit) is read from the script, not fixed: it differs between 2.0.25, 2.0.26 and 2.1.0.
* Version 2.0.25 only: the function MoonVeil compiled to its own VM is read back too, without running anything (data layout, opcode table and instruction layouts are taken from the script’s own interpreter code).
* Versions 2.0.26 and 2.1.0: strings and numbers are decoded (for the one 2.0.26 script with a hand-made reference, 77 of its 81 string literals are in the output, including every URL), but the VM reader does not fit the interpreter of these builds ("the interpreter does not have the expected shape") and the control-flow-flattened functions are not all unflattened (the initial state of the dispatcher is not a constant). The program stays a table of decoded functions; fidelity against the reference is 21%. The confidence is capped for that reason (0.60, medium); it was 0.90 before this was measured.
* Version 1.4.5: a different layout (no function table): constants and cells are decoded, three dispatcher loops of 8, 135 and 259 blocks remain, and a 28888-character encoded blob is left. No reference exists, so fidelity is not measured; the confidence is low (0.50).
* MV_CFF, MV_ENC_FUNC and MV_VM are the vendor’s documented macros (per-function virtualisation, encryption keyed at run time, control-flow flattening, MV_OMIT to exclude one); MV_ENC_FUNC bodies need their run-time key and are not recovered. The vendor’s documentation site could not be read from this environment, so the macro list is from search results quoting it.

**Documented techniques with no fixture:** optional VM, function encryption, control-flow flattening, closure table with cell variables, Z85 + XOR string encryption, bit32 arithmetic constants

## XFuscator

Extracts constants into a pool, renames locals, optionally encrypts strings with XOR and "uglifies" words; ends in a step that writes the program as an array of scaled character codes run through loadstring, with a length check as tamper detection. Its precompile step reads Lua 5.1 bytecode through a library that only works on 32-bit builds.

**Status:** partial (real-output). The step-2 closure `string.char(x / scale)` with a table of its calls and the decimal-escaped tamper string "XFU5K470R R00LZ", read on output of the tool run in the isolated Lua state.

| Configuration | Status | Fidelity before → after | Same behaviour | Mean time |
|---|---|---|---|---|
| default (preset) | supported | 1% → 97% | 8 / 8 | 97 ms |
| uglify (preset) | supported | 1% → 97% | 8 / 8 | 89 ms |
| encrypt (preset) | supported | 1% → 94% (needs sandbox) | 0 / 0 (8 tool output broken) | 585 ms |
| nostep2 (preset) | supported | 3% → 97% | 8 / 8 | 25 ms |
| notamper (preset) | supported | 1% → 97% | 8 / 8 | 96 ms |

**Limits**

* The program kept as an array of scaled character codes is read by finding the scale that makes every entry divide and the text parse; the encrypt option (XOR through `bit or bit32 or require`) is evaluated in the sandbox. Fidelity is 88% to 100% wherever the original names survive and 48% to 60% where they were descriptive (locals are renamed).
* The precompile option (`loadstring`) was not generated: the tool’s LAT library needs a 32-bit Lua build. Three options crash inside the tool itself (nofluff, comments, level2) and are recorded as tool errors.
* Output is kept local (the repository states no licence).

**Documented techniques with no fixture:** fluff, length check

## IronBrew 2

Open-source (MIT) Lua 5.1 obfuscator in C# that compiles a script with luac and re-emits it as a custom register VM plus a compressed, XOR-masked program string.

**Status:** supported (real-output). The prelude (LZW + XOR deserialiser, wrapper function names) is matched structurally; the opcode handlers are matched by alpha-equivalent form against the handler templates in IronBrew 2's own C# source.

| Configuration | Status | Fidelity before → after | Same behaviour | Mean time |
|---|---|---|---|---|
| default (preset) | supported | 4% → 88% | 8 / 8 | 71 ms |
| plain (preset) | supported | 8% → 90% | 8 / 8 | 57 ms |
| mutate (preset) | supported | 6% → 90% | 8 / 8 | 71 ms |
| super (preset) | supported | 5% → 90% | 8 / 8 | 71 ms |
| flow (preset) | supported | 8% → 88% | 3 / 3 (5 tool output broken) | 64 ms |
| strings (preset) | partial | 3% → 84% | 8 / 8 | 566 ms |
| lineinfo (preset) | supported | 4% → 88% | 8 / 8 | 73 ms |
| nocompress (preset) | supported | 4% → 88% | 8 / 8 | 67 ms |

**Detection on real scripts:** 7 of 8 files filed under IronBrew2 in the public collection (https://github.com/vyxonq-dev/obfuscator-samples, commit `82e582fcdd`) were identified as IronBrew 2. The collection's labels are its uploaders' and are noisy; a file our rules call something else was looked at before being counted as a miss.

**Limits**

* Recovery reads the embedded chunk instead of running the VM: handlers are identified by shape, operand transforms are solved symbolically, the Lua 5.1 chunk is rebuilt and decompiled. A handler that matches no template stops the recovery with an error instead of guessing.
* Local variable names, comments and the original function layout are not in the bytecode, so they are not recoverable (names are regenerated; some local functions come back as expressions).
* The "strings" option decrypts every literal with a routine written out in place. Recovery finds those stretches (only constants, only pure standard functions, no closures) and replaces each by the text it computes, using the sandbox interpreter on that stretch alone; it needs no consent because nothing but the stretch is run. Other register-reuse noise remains, so the result is partial.
* The "flow" option of the real tool produced output that does not run correctly on its own for five of eight samples (see the "tool broken" column); recovery there is judged against the original program, not against the broken output.
* Only IronBrew 2 as built from the public MIT source is covered. Forks that change the VM template or the serialiser need their own templates.

## Colisseum

Open-source (AGPL-3.0) Lua / Luau obfuscator written in Lua (de-TourLLC). Presets easy, medium, hard and full are source-level; total and fortress compile the program for a VM.

**Status:** partial (real-output). Signatures verified against output of the real tool for every preset: the credit line, the error brand, the coli_ names, the tamper guard block and the VM entry call. The AGPL-3.0 licence of the tool does not allow committing its output, so the fixtures are generated locally (tests/corpus/tools/gen_external.py, run through the isolated runner) and the tests that use them skip when they are absent.

**Limits**

* easy, medium, hard and full are source-level: the tamper guard is recognised by its strings and removed without being run, the string decryptor is evaluated in the sandbox, and the junk branches are dropped. The output prints what the original program prints; names are guesses from use.
* The decryptor multiplies past 2^53 and was written for Lua 5.4 integers (it gives noise on Lua 5.1, LuaJIT and Luau doubles). The sandbox therefore evaluates it both ways and keeps the reading that is text; if neither is, the strings are left encoded and the report says so. Without the sandbox the strings stay encoded.
* total (native VM) and fortress (register VM with an encrypted bytecode blob) are detected from the VM entry call and flagged as not recovered: the program exists only as data for an interpreter. Recovery is not attempted.
* The behavioural trace is stopped by the tamper guard of every preset except easy, because the trace’s stand-in environment defines executor functions and the guard counts them (error 0x6B0C). Remove the guard first (medium, hard, full: Deobfuscate, then Trace the result). In the plain sandbox total runs to the end and fortress stops at 0x3E44 (the guard sees the sandbox’s debug library is not native).
* The total and fortress fixtures only run without an instruction-count hook, on LuaJIT: their anti-tamper treats a hook as an attack, so they were verified with tests/corpus/tools/run_lua_nohook.py.

**Documented techniques with no fixture:** minify and rename (coli_ names), encrypted strings, constant arrays / split strings, control-flow flattening and opaque predicates, tamper guard (debug hook, executor globals, replaced standard functions, line-number check), native VM (total), register VM with ChaCha20-encrypted bytecode (fortress)

* Three of the eight outputs of the page itself do not behave like their originals (its regular-expression renaming breaks some programs), so behaviour is only compared for the other five.
* The author says in the page itself that it gives no meaningful protection. The numbers here measure how much of the original is recovered, not how strong the tool is.
