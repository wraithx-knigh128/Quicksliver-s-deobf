# Compatibility

Generated by `tools/build-compat.mjs` from `tests/results/*.json` (481 fixtures, engine 1.0.0). Do not edit by hand.

Fidelity is the overlap between the recovered code and the original program the fixture was made from (identifier names ignored). Behaviour compares what the recovered script prints with what the
obfuscated one printed, on a real Lua (PUC 5.1 / LuaJIT / 5.4 through `lupa`). A technique is **supported** when fidelity is at least 85% and behaviour matches; **partial** when it is better than before
but short of that; **unsupported** otherwise. Families without fixtures are signatures only (**experimental** or **unsupported**): nothing was run and nothing is claimed.

## MoonVeil

Commercial obfuscator (moonveil.cc) with selectable virtualisation, function encryption and control-flow flattening (macros MV_VM, MV_ENC_FUNC, MV_CFF, MV_OMIT). One real output was read (banner "generated using MoonVeil 2.0.25"): functions lifted into a table, flattened bootstrap code, Z85 + XOR strings, bit32 expressions for numbers, and VM-compiled functions stored as one compressed Z85 text (read back from that data by the VM reader when the interpreter has the shape of the script that was studied).

**Status:** partial (signature). Taken from one real script (a MoonVeil 2.0.25 script supplied by a user and not stored here): the table-and-permutation shape is recognised structurally, the banner by its text. No MoonVeil output could be generated here (the tool is closed and hosted), so there is no scorecard row; the claims below rest on that one script.

**Limits**

* Read back statically from the one script: the strings (Z85 text plus an XOR cipher), the numbers (bit32 expressions) and the table of cells, which makes the program’s plain Lua readable.
* The function MoonVeil compiled to its own VM is read back too, without running anything. How its data is laid out (field ids, opcode table, instruction layouts), which cell of the interpreter is which builtin and what its helper methods do are all taken from the script’s own interpreter code, so they are not fixed in this tool. The data is decoded, the encrypted part of it is opened by searching for the one small number its key depends on, and every instruction is partially evaluated against the interpreter’s own handlers and structured back into Lua.
* A build whose interpreter has a different shape is not guessed at: the step says which part did not fit and the general passes take over. Only version 2.0.25 and one script were looked at, so other builds and settings (MV_CFF, MV_ENC_FUNC) are unconfirmed.
* Not compared with a run of the original: the report says so and keeps the confidence at medium. A generic for loop of a shape the reader does not know stays as a call to forgprep (the VM’s own step; none is left in the script that was studied), and register capture follows the VM’s model rather than Lua’s scoping, so a few locals are shared where the source had separate ones.

**Documented techniques with no fixture:** optional VM, function encryption, control-flow flattening, closure table with cell variables, Z85 + XOR string encryption, bit32 arithmetic constants

## Kirus

Obfuscator that stamps "This file was protected by Kirus obfuscator v1.5". No public source or documentation was found. One real output was read: a bytecode VM written in Lua with a custom base-85 blob, runtime-keyed constant pools and encrypted instruction regions.

**Status:** unsupported (signature). Taken from one real script (supplied by a user and not stored here): the banner comment and the entry call setmetatable({...}, {}):name(bit32, string, table, math, type, error, pcall, getfenv or debug.getfenv, ...). Nothing else was available.

**Limits**

* A bytecode VM with a custom base-85 container, a keystream and rotation, opaque-predicate dispatch and runtime-keyed constants. The container was cut into regions and measured, not decoded; the program is not recovered.
* The identifiers the VM builds from XOR pairs are decoded by plain arithmetic on literals (loadstring, getgenv, setfenv, getrawmetatable, executor names). That shows what the runtime touches, not what the program does.
* The behavioural trace can say what an authorised run of it does, but only when the user switches it on. Nothing was run for this project.

**Documented techniques with no fixture:** bytecode VM, custom base-85 encoding, XOR-built identifier strings, runtime-keyed constants, integrity checks

## IronBrew 2

Open-source (MIT) Lua 5.1 obfuscator in C# that compiles a script with luac and re-emits it as a custom register VM plus a compressed, XOR-masked program string.

**Status:** supported (real-output). The prelude (LZW + XOR deserialiser, wrapper function names) is matched structurally; the opcode handlers are matched by alpha-equivalent form against the handler templates in IronBrew 2's own C# source.

| Configuration | Status | Fidelity before → after | Same behaviour | Mean time |
|---|---|---|---|---|
| default (preset) | supported | 4% → 91% | 8 / 8 | 52 ms |
| plain (preset) | supported | 8% → 93% | 8 / 8 | 41 ms |
| mutate (preset) | supported | 6% → 93% | 8 / 8 | 42 ms |
| super (preset) | supported | 5% → 93% | 8 / 8 | 43 ms |
| flow (preset) | supported | 8% → 91% | 8 / 8 (5 tool output broken) | 40 ms |
| strings (preset) | partial | 3% → 77% | 8 / 8 | 507 ms |
| lineinfo (preset) | supported | 4% → 91% | 8 / 8 | 52 ms |
| nocompress (preset) | supported | 4% → 91% | 8 / 8 | 44 ms |

**Limits**

* Recovery reads the embedded chunk instead of running the VM: handlers are identified by shape, operand transforms are solved symbolically, the Lua 5.1 chunk is rebuilt and decompiled. A handler that matches no template stops the recovery with an error instead of guessing.
* Local variable names, comments and the original function layout are not in the bytecode, so they are not recoverable (names are regenerated; some local functions come back as expressions).
* The "strings" option decrypts every literal with a routine written out in place. Recovery finds those stretches (only constants, only pure standard functions, no closures) and replaces each by the text it computes, using the sandbox interpreter on that stretch alone; it needs no consent because nothing but the stretch is run. Other register-reuse noise remains, so the result is partial.
* The "flow" option of the real tool produced output that does not run correctly on its own for five of eight samples (see the "tool broken" column); recovery there is judged against the original program, not against the broken output.
* Only IronBrew 2 as built from the public MIT source is covered. Forks that change the VM template or the serialiser need their own templates.

## Colisseum

Open-source (AGPL-3.0) Lua / Luau obfuscator written in Lua (de-TourLLC). Presets easy, medium, hard and full are source-level; total and fortress compile the program for a VM.

**Status:** partial (real-output). Signatures verified against output of the real tool for every preset: the credit line, the error brand, the coli_ names, the tamper guard block and the VM entry call. The AGPL-3.0 licence of the tool does not allow committing its output, so the fixtures are generated locally (tests/corpus/tools/gen_external.py, run through the isolated runner) and the tests that use them skip when they are absent.

| Configuration | Status | Fidelity before → after | Same behaviour | Mean time |
|---|---|---|---|---|
| easy (preset) | supported | 67% → 100% | 8 / 8 | 7 ms |
| medium (preset) | supported | 11% → 100% (needs sandbox) | 8 / 8 | 22 ms |
| hard (preset) | supported | 10% → 100% (needs sandbox) | 8 / 8 | 23 ms |
| full (preset) | supported | 9% → 100% (needs sandbox) | 8 / 8 | 24 ms |
| total (preset) | unsupported | 3% → 3% | 0 / 8 | 1566 ms |
| fortress (preset) | unsupported | 3% → 3% | 0 / 8 | 192 ms |

**Limits**

* easy, medium, hard and full are source-level: the tamper guard is recognised by its strings and removed without being run, the string decryptor is evaluated in the sandbox, and the junk branches are dropped. The output prints what the original program prints; names are guesses from use.
* The decryptor multiplies past 2^53 and was written for Lua 5.4 integers (it gives noise on Lua 5.1, LuaJIT and Luau doubles). The sandbox therefore evaluates it both ways and keeps the reading that is text; if neither is, the strings are left encoded and the report says so. Without the sandbox the strings stay encoded.
* total (native VM) and fortress (register VM with an encrypted bytecode blob) are detected from the VM entry call and flagged as not recovered: the program exists only as data for an interpreter. Recovery is not attempted.
* The behavioural trace is stopped by the tamper guard of every preset except easy, because the trace’s stand-in environment defines executor functions and the guard counts them (error 0x6B0C). Remove the guard first (medium, hard, full: Deobfuscate, then Trace the result). In the plain sandbox total runs to the end and fortress stops at 0x3E44 (the guard sees the sandbox’s debug library is not native).
* The total and fortress fixtures only run without an instruction-count hook, on LuaJIT: their anti-tamper treats a hook as an attack, so they were verified with tests/corpus/tools/run_lua_nohook.py.

**Documented techniques with no fixture:** constant arrays / split strings, control-flow flattening and opaque predicates
